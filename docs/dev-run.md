# Локальный запуск (dev)

Три терминала из корня репозитория (`export PATH="$HOME/.cargo/bin:$PATH"`
для Rust, если ещё не в `PATH`).

**Терминал 1 — сигнальный сервер:**

```
cargo run -p rcdesk-server
```

Слушает `127.0.0.1:8080`, маршрут `/ws`.

**Терминал 2 — хост-агент:**

```
cargo run -p rcdesk-host -- serve --synthetic
```

`--synthetic` — генератор кадров вместо реального захвата экрана (не
требует разрешения «Запись экрана»). Без разрешения на Mac реальный захват
не запустится — выдайте его в Системные настройки → Конфиденциальность и
безопасность → Запись экрана, затем запускайте `serve` без `--synthetic`.

Команда напечатает PIN, например:

```
PIN: 123456
```

## ICE-серверы (STUN/TURN)

По умолчанию `serve` не задаёт свой список ICE-серверов: он использует то,
что пришло от сигнального сервера в `Registered` (см. `server/src/ice.rs`) --
локально это один STUN `stun:stun.l.google.com:19302` (дефолт сервера без
`RCDESK_*` переменных). Флаг `--stun <url>` (повторяемый) добавляет ещё
серверы поверх присланных сервером, а не заменяет их.

## Подключение к проду

```
cargo run -p rcdesk-host -- serve --server wss://rcdesk.app/ws
```

`tokio-tungstenite` собран с `rustls-tls-webpki-roots`, так что `wss://`
работает без дополнительной настройки TLS.

**Терминал 3 — веб-клиент:**

```
cd web && npm run dev
```

Откройте `http://localhost:5173`, введите PIN из терминала 2, нажмите
Connect. Vite dev-сервер проксирует `/ws` на `ws://127.0.0.1:8080` (см.
`web/vite.config.ts`) — в проде эту роль играет Caddy.

## Проверка в Safari

Тот же URL, `http://localhost:5173`, в Safari на этой же машине (или другой
машине в той же сети — тогда вместо `localhost` укажите LAN-адрес хоста, на
котором запущены сервер и `npm run dev`). Ввод PIN и подключение — как в
Chrome. Safari требует, чтобы `video.play()` вызывался в рамках жеста
пользователя (клик по Connect) — это уже учтено в `web/src/app.ts`.

## Кодер видео

`--encoder auto|openh264|videotoolbox|mediafoundation` и `--max-qp N` у `bench`
и `serve`. На macOS `auto` берёт аппаратный VideoToolbox (в логе
`initializing videotoolbox encoder … hardware=true`), при ошибке создания —
openh264 с предупреждением. Сравнить кодеры без сети:

```
cargo run -p rcdesk-host --release -- bench --seconds 5 --encoder videotoolbox
cargo run -p rcdesk-host --release -- bench --seconds 5 --encoder openh264
```

`bench` печатает `encoder=…`, размеры ключевых/дельта-кадров и задержку
захват→кодер (`avg_capture_to_encoded_ms`). `--max-qp N` ставит потолок QP
(резче текст, выше битрейт); без флага у openh264 потолок 30, у VideoToolbox
и Media Foundation потолка нет. Для VideoToolbox флаг задаёт
`MaxAllowedFrameQP`, на старых macOS ключ может быть отклонён — тогда в логе
`warn` и работа без него. Windows-кодер Media Foundation описан в
`docs/host-windows.md`.

## Адаптация битрейта/fps

По умолчанию `serve` держит фоновый контроллер (слайс 2.3, `host/src/adapt/`),
который раз в секунду смотрит на обратную связь от клиента и решает, стоит ли
менять цель кодера. Источники: REMB и потери пакетов из RTCP (`Receiver
Report`) — REMB ниже того, что хост реально отправил (при нагруженном канале,
два тика подряд), режет битрейт (`reason "remb"`), высокие потери режут его
агрессивнее (`reason "loss"`), а
здоровый канал даёт битрейту расти пробным шагом +10 % в тик (`reason
"probe"`); отдельно контроллер следит за перезаписью слота захвата (кадр
пришёл, пока кодер занят предыдущим) — если кодер не успевает, fps ступенчато
падает (`reason "encoder"`), а если на
текущем битрейте/fps бюджет кадра слишком мал (меньше 0.02 бит/пиксель/кадр),
fps срезается независимо от кодера (`reason "bitrate"`). Отключить:

```
cargo run -p rcdesk-host -- serve --synthetic --no-adapt
```

Тогда кодер держит `--bitrate`/`--fps` неизменными всю сессию — удобно для
замеров "до/после". Каждое решение контроллера видно двумя способами: в логе
хоста строкой `adapt: new rate target` (с `bitrate_kbps`, `fps`, `reason`), и
в оверлее клиента — сегментом `target 3.2 Mbit/s @ 20 fps (remb)`, который
появляется после первого решения (при `--no-adapt` не появляется вовсе).

## Ввод (мышь и клавиатура)

**⚠️ Без `--no-input` подключившийся клиент управляет настоящими мышью и
клавиатурой хоста** — как только сессия установлена, движения курсора,
клики и нажатия клавиш в браузере клиента реально выполняются на машине,
где запущен `rcdesk-host`. Проверяйте это осознанно, не на рабочей машине
без присмотра.

Флаг `--no-input`:

```
cargo run -p rcdesk-host -- serve --synthetic --no-input
```

Сообщения `input`/`pointer` при этом принимаются и логируются
(`RUST_LOG=debug`), но ничего не подаётся в реальные мышь/клавиатуру —
безопасный способ проверить сессию целиком (PIN, WebRTC, data channels) без
риска потерять управление собственной машиной.

На macOS реальная инъекция (без `--no-input`) требует разрешения
**Универсальный доступ**: Системные настройки → Конфиденциальность и
безопасность → Универсальный доступ → включите приложение терминала (или
`rcdesk-host`), из которого запущен хост. Без этого разрешения события
мыши/клавиатуры на macOS не доставляются — молча, без ошибки в логах.

Буфер обмена (текст, в обе стороны) синхронизируется по умолчанию; флаг
`serve --no-clipboard` отключает это для всей сессии (слайс 2.5b).

## Курсор

Форма системного курсора (стрелка, I-beam, рука, resize и т.д.) приходит с
хоста по каналу `control` (`ControlMessage::CursorShape`/`CursorHidden`) и
применяется в клиенте как CSS `cursor: url(...)` на `<video>` (см.
`web/src/cursor.ts`). Сам курсор в захват видео не попадает (`show_cursor:
false`) и рисуется браузером локально с нулевой задержкой — по каналу едет
только его форма, и то лишь когда она меняется. На macOS форма читается
через `NSCursor.currentSystemCursor`, разрешение «Запись экрана» для этого
не требуется. На платформах без реализации (Linux и т.п.) хост использует
`NoopCursorSource` — клиент показывает свой обычный курсор браузера.

Раз в секунду клиент шлёт по каналу `control` `ping` и по ответному `pong`
считает прикладной round-trip (в отличие от `rtt` в оверлее, который берётся
из `getStats()` и меряет только уровень WebRTC/ICE). Результат показан в
оверлее сессии как `app N ms`.

## Мультимонитор

```
cargo run -p rcdesk-host -- list-displays
```

Список дисплеев, колонки через табуляцию: `id  title  WxH@x,y  primary|-`
(`x,y` — левый верхний угол в OS-глобальных координатах, `primary` или `-`).

```
cargo run -p rcdesk-host -- serve --synthetic --display <id>
```

`--display <id>` выбирает дисплей для захвата по `id` из `list-displays`; без
флага захватывается основной (primary) дисплей.

В панели сессии веб-клиента селектор дисплеев появляется автоматически, как
только хост сообщает два дисплея и более (`ControlMessage::Displays`), и
скрыт при одном. Выбор в селекторе шлёт `select_display` по каналу `control`
и переключает транслируемый дисплей без разрыва сессии (WebRTC-соединение и
все data channel остаются открытыми).

Проверить локально без второго физического монитора — `--synthetic` без
`--display` даёт два фейковых дисплея: `1: Synthetic 1 1280×720 (primary)` с
горизонтальным градиентом и `2: Synthetic 2 1024×768` с вертикальным, так что
переключение видно на глаз. `--synthetic --display 2` стартует сразу со
второго.
