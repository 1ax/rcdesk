# rcdesk — Архитектура

> Документ решений. Меняется только осознанно, с записью в SLICES_LOG.md.
> Актуально на 2026-09-18 (слайс 2.6).

## 1. Цель и границы

Удалённое управление рабочим столом macOS и Windows **из браузера** (Safari и
Chrome как минимум) с максимальной производительностью: низкая задержка, высокий
fps, аппаратное кодирование. Ориентир — Chrome Remote Desktop.

Аудитория на старте: владелец и небольшая команда (до десятков хостов). Публичный
масштаб не проектируем, но не закрываем: авторизация и сигналинг делаются так,
чтобы добавить учётки и подписи кода без переписывания.

Не делаем (пока): Linux-хост, мобильные клиенты, нативные клиенты.

## 2. Стек и обоснование

| Слой | Выбор | Почему |
|---|---|---|
| Хост-агент | **Rust**, один код для macOS и Windows | Единственный вариант «один бинарник, нативная скорость, без рантайма» с живыми крейтами под захват, кодек, WebRTC и ввод. Go требует cgo под ScreenCaptureKit/DirectX; Electron — 200 МБ и лишний слой. |
| Захват экрана | `scap` (ScreenCaptureKit на macOS, Windows Graphics Capture на Windows); на Windows запасной **GDI** (`BitBlt`) | Единый API поверх нативных zero-copy захватов. Используется в проде (Cap.so). Если упрёмся — прямые `screencapturekit` / `windows-capture`. WGC требует Direct3D 11 у драйвера; на легаси-драйверах и в ВМ хост сам уходит на GDI (`--capture auto`, слайс 2.1). |
| Кодек, запасной | `openh264` (Cisco, программный) | Портативно, лицензионно чисто, достаточно для 1080p30 на M4/современном x64. Запасной путь, если нативный кодер не создался, и единственный вне macOS/Windows. Потолок QP 30 по умолчанию (`--max-qp`) против размытого текста. |
| Кодек, аппаратный | VideoToolbox (macOS) через `objc2-video-toolbox`; Media Foundation H.264 MFT (Windows) через `windows` (слайс 2.2) | Аппаратное кодирование без зависимости от ffmpeg. `--encoder auto`: VT на macOS; на Windows — любой MFT, аппаратный первым, программный Microsoft вторым (на стенде он быстрее и резче openh264, слайс 2.2); при ошибке создания — откат на openh264. Кодер сам конвертирует `RawFrame` в свой вход (VT и MF — NV12, openh264 — I420). |
| WebRTC на хосте | `webrtc` (webrtc-rs, порт pion) | Полный стек (ICE/DTLS/SRTP/SCTP), interceptors NACK/TWCC, API знаком по pion. Развилка на будущее: `str0m` (sans-IO, встроенный BWE), если упрёмся в управление битрейтом. |
| Ввод | `enigo` (CGEvent на macOS, SendInput на Windows) | Живой, кроссплатформенный. |
| Буфер обмена | `arboard` | Текст и изображения на обеих платформах. |
| Async/логи/ошибки | `tokio`, `tracing`, `thiserror` + `anyhow` | Стандарт. |
| Общие типы протокола | крейт `proto` + `ts-rs` | Один источник правды для Rust и TypeScript; TS-типы генерируются, не пишутся руками. |
| Веб-клиент | **TypeScript** + Vite, без UI-фреймворка (при росте UI — Preact) | Клиент — это `<video>`, canvas курсора, обработчики ввода и панель. Фреймворк не нужен. |
| Сигнальный сервер | **Rust**, `axum` + `tokio-tungstenite` | Один язык с хостом, общие типы из `proto`. Нагрузка ничтожна. |
| TURN/STUN | `coturn` в Docker | Стандарт де-факто. |
| Реверс-прокси/TLS | nginx из FastPanel на VPS владельца (как в crewtally) | Порты 80/443 на VPS уже за FastPanel; LE-сертификат выпускает панель. `.app` — зона с принудительным HTTPS (HSTS preload), что нам и нужно. Caddy — запасной вариант для чистого сервера. |
| CI | GitHub Actions: `macos-latest`, `windows-latest`, `ubuntu-latest` (web, server) | Публичный репо — без лимита минут. Deploy собирает release-бинарники хоста как артефакты (`rcdesk-host-windows-x64`, `rcdesk-host-macos-arm64`), каждый теперь содержит оба бинарника пакета — `rcdesk-host[.exe]` и `rcdesk-agent[.exe]` (2.6d): кросс-компиляции нет, openh264 собирается под MSVC. |

Версии крейтов на момент выбора (crates.io, 2026-09-11): `webrtc` 0.20.5, `str0m`
0.23.1, `scap` 0.0.8, `enigo` 0.6.1, `openh264` 0.9.8, `windows-capture` 2.0.1,
`screencapturekit` 10.0.3, `objc2-video-toolbox` 0.3.2. Точные версии фиксирует
`Cargo.lock`.

## 4. Компоненты

### 4.1 Хост-агент (`host/`)

Долгоживущий процесс пользователя (лёгкий режим) или служба (полный режим, фаза 4).
Держит WS-соединение с сигнальным сервером, по запросу клиента поднимает
`RTCPeerConnection`, публикует видеотрек и принимает data channels.

Конвейер видео: `FrameSource` → `Encoder` (принимает `RawFrame`, конверсию в
свой входной формат делает сам и ставит `captured_at` из времени захвата) →
RTP-пакетизатор webrtc-rs → сеть. Один рабочий поток на захват, один
на кодирование, транспорт на tokio. Между ними — ограниченные каналы с политикой
«держать только последний кадр» (старый кадр важнее сбросить, чем доставить).

Пейсинг: целевой fps задаётся клиентом (30/60), кадр кодируется только если
источник сообщил об изменении (SCK/WGC отдают кадры только при изменении экрана —
статичный экран стоит ~0 трафика). Ключевой кадр — по PLI/FIR от клиента и при
подключении.

Экран сразу после подключения (слайс 2.6f): если запрошен ключевой кадр, а новый
кадр от источника не пришёл за `SLOT_WAIT_TIMEOUT` (статичный экран), кодер-поток
перештамповывает временем «сейчас» и кодирует как ключевой последний захваченный
кадр вместо ожидания следующего изменения на экране — иначе подключившийся клиент
видит чёрный экран, пока хост не изменится.

Мультимонитор (слайс 2.4): захват + кодер + контроллер адаптации живут в
`VideoPipeline` на один дисплей. По `control: SelectDisplay` хост поднимает новый
`VideoPipeline` для выбранного дисплея и только потом гасит старый (отказ оставляет
прежнюю трансляцию); `PeerConnection`, трек, data channels и роутер ввода не
пересоздаются, все pipeline сессии пишут в один канал `start_video` и делят один флаг
keyframe. Старый pipeline останавливается через `spawn_blocking`: capture-поток SCK
может висеть в `get_next_frame` до следующего изменения экрана. Список дисплеев
(`control: Displays`, id/название/размер/primary) уходит клиенту при открытии `control`
и после каждого переключения; без `--display` берётся primary. На Windows список —
свой `EnumDisplayMonitors` (`platform::windows::monitors`), id = HMONITOR, как у scap.

Агент в трее (2.6c): второй бинарник, `rcdesk-agent` (macOS меню-бар / Windows трей),
поверх того же `app::run_agent`; `rcdesk-host` не меняется. Главный поток занят
собственным минимальным циклом событий (`platform::{macos,windows}::event_loop::pump`,
без winit/tao — см. §14) и меню `tray-icon`/`muda`; `run_agent` крутится на отдельном
`tokio::runtime::Runtime` (не `#[tokio::main]`), общаются через `watch<AgentStatus>` и
`mpsc::UnboundedSender<AgentCommand>` (`EndSession`). Лог — файл (`agent::paths::log_dir()`:
`~/Library/Logs/rcdesk/agent.log` / `%LOCALAPPDATA%\rcdesk\logs\agent.log`, ротация от 5 МБ)
вместо stderr; один экземпляр — лок-файл в `agent::paths::data_dir()`. На время активной
сессии хост держит систему от сна: `NSProcessInfo` activity (macOS) / `SetThreadExecutionState`
(Windows) — иначе App Nap/сон душит фоновый процесс без окон.

### 4.2 Веб-клиент (`web/`)

Одна страница. Подключается к сигнальному серверу по WSS, получает список хостов,
устанавливает WebRTC-сессию. `<video>` с `playsinline`, `autoplay`, `muted`;
поверх — canvas локального курсора. Захват ввода: `pointermove` с
`getCoalescedEvents`, `keydown/keyup` по `event.code` (физическая клавиша, не
символ), колесо с нормализацией `deltaMode`. Pointer Lock по клику,
Keyboard Lock в Chrome в полноэкранном режиме. Оверлей статистики
(`getStats()`: fps, битрейт, RTT, jitter, потери, кодек). Селектор дисплеев в панели
сессии появляется при двух и более дисплеях и блокируется до ответа хоста `Displays`.
Идентификатор сборки (слайс 2.6f): `build <short sha>` (`dev` вне CI), приглушённой
подписью поверх обоих экранов — чтобы вкладка, оставшаяся открытой с прошлого
деплоя, была видна на глаз, а не молча работала на старом протоколе.

### 4.3 Сигнальный сервер (`server/`)

Хосты регистрируются по WSS с `device_id` + токеном устройства; клиенты
подключаются по WSS. Сервер только пересылает SDP/ICE между парами и отдаёт
список онлайн-хостов. Состояние в памяти (MVP) → SQLite (фаза 3: устройства,
пользователи). Выдаёт короткоживущие TURN-креды (coturn REST API, HMAC).
TURN-креды выдаются в `Registered`, `Joined` и `PeerJoined`: хост берёт
свежие на каждый сеанс (2.6b).

### 4.4 Общие типы (`proto/`)

Все сообщения — `serde` структуры с `#[derive(TS)]`; `cargo test -p proto`
генерирует `web/src/generated/*.ts`, CI проверяет, что сгенерированное совпадает
с закоммиченным. Никакого кода с логикой.

## 5. Транспорт: WebRTC

- **Видео:** один трек, H.264, `packetization-mode=1`, профиль
  Constrained Baseline `42e01f` (единственный, который гарантированно аппаратно
  декодируют и Safari, и Chrome). Позже — переговоры High `640032` для Chrome и
  AV1 как опция. Без B-кадров, без открытых GOP, `max-fr`/`max-fs` не ограничиваем.
- **Data channels** (SCTP):
  - `input` — надёжный, упорядоченный: клавиши, кнопки мыши, колесо; буфер обмена клиент → хост
    (`ClipboardText` в одном потоке с клавишами: буфер хоста обновлён строго до следующего Cmd+V).
  - `pointer` — `ordered: false, maxRetransmits: 0`: движения мыши (потерянное
    движение не важно, следующее его заменит).
  - `control` — надёжный: буфер обмена хост → клиент, смена монитора, качество, курсор, пинг, статус ввода,
    предупреждение об окне с повышенными правами (Windows, `InputBlocked`, 2.6e).
  - `file` — надёжный, чанки 64 КБ с backpressure по `bufferedAmount`.
- **RTP-время видео:** отметка кадра = реальное время захвата (транспорт пакетизирует сам:
  `TrackLocalStaticRTP` + `Packetizer`, `skip_samples` на интервал между захватами). Фиксированный
  шаг `1/fps` недопустим: кадры идут только при изменении экрана, и Chrome копил ~850 мс в jitter-буфере.
- **Кодирование сообщений:** JSON (MVP; типы из `proto`). Если измерение покажет
  накладные расходы на `pointer` — компактный бинарный формат, решение фазы 2.
- **Управление битрейтом (слайс 2.3):** контроллер на хосте (`host/src/adapt`), тик раз в
  секунду, входы — **REMB** от браузера (оценка его receive-side GCC, ограничена ~1.5× принятого
  и растёт ~8 %/с; сигнал перегрузки только когда канал нагружен — отправлено ≥ 80 % цели — и REMB
  ниже отправленного два тика подряд и при этом не растёт — растущий REMB просто догоняет поток;
  иначе на статичном экране или на старте видео он режет цель без причины),
  **доля потерь из RTCP RR** (> 10 % — срез; при отсутствии сигналов перегрузки и потерь < 2 % —
  пробинг +10 %/с, единственный путь вверх) и **перезапись слота захвата** (кадр пришёл, пока кодер
  занят предыдущим, ≥ 2 за тик — ступень fps вниз; пять чистых тиков — вверх).
  Порядок «сначала fps, потом битрейт» — через бюджет кадра (0.02 бит/пиксель): при низком
  битрейте fps опускается раньше, чем картинка станет мылом. Разрешение не меняется (долг
  на будущее). Выходы: `Encoder::set_rate` (без пересоздания кодера) и пейсинг fps в
  конвейере до кодера. `--no-adapt` отключает для замеров «до/после».
  **TWCC на хосте не включён намеренно:** `register_default_interceptors` ставит TWCC
  только на приём; если добавить расширение в исходящие пакеты, Chrome перестанет слать
  REMB и оценку (GCC) придётся писать самим — развилка на будущее (или `str0m`).
- **ICE:** STUN + TURN (udp/tcp/tls на 443 для корпоративных сетей).
- **Шифрование:** DTLS-SRTP (WebRTC), DTLS для SCTP. Сервер видит только сигналинг.

## 6. Сигналинг и авторизация

Транспорт — WSS, сообщения JSON из `proto::signal`.

**MVP (фаза 1):** хост при запуске показывает 6-значный PIN, клиент вводит PIN,
сервер сводит пару. PIN живёт до первого подключения или 10 минут.

**Фаза 3:** устройство получает постоянный `device_id` + секрет (регистрация по
PIN один раз), пользователь — учётку (email + пароль или magic link). Пароль
доступа к хосту проверяется **на хосте** через PAKE (OPAQUE или SPAKE2), сервер
и TURN не знают секрета и не могут подключиться сами. Подтверждение отпечатка
DTLS-сертификата хоста в клиенте — защита от подмены на сервере.

## 7. Ввод

Клиент шлёт `event.code` (например `KeyA`, `MetaLeft`) и состояние модификаторов;
хост переводит в платформенный виртуальный код (macOS — kVK_*, Windows — VK_*).
Раскладка символов — задача хоста, как при физической клавиатуре. Для текста,
который браузер не может выразить кодом (IME, вставка), — отдельное сообщение
`Text { string }` → `enigo.text()`.

Координаты мыши — нормализованные `[0,1]` относительно транслируемого монитора, хост
масштабирует их в прямоугольник этого монитора в глобальных координатах ОС
(`input::CaptureRect` из `capture::DisplayInfo`: точки CGEvent на macOS, физические
пиксели виртуального экрана на Windows) — не зависит от HiDPI и масштаба видео. На
Windows абсолютное перемещение идёт своим `SendInput` с `MOUSEEVENTF_VIRTUALDESK`
(`platform::windows::mouse`): `enigo` нормализует только по primary-монитору. Курсор
рисуется локально в клиенте по форме, присланной хостом (`control: CursorShape`),
в видео курсор не попадает — экономия битрейта и нулевая задержка курсора.

Если инжектор ввода не поднялся (macOS без «Универсального доступа», `serve --no-input`), сеанс не
гаснет: хост подставляет `NoopInjector` и при открытии `control` шлёт `InputStatus { available: false,
reason }`, клиент не цепляет ввод и показывает `View only: <причина>` (2.5a, D26). Статус определяется
на старте сессии; после выдачи разрешения достаточно переподключиться.

## 8. Два режима хоста

| | Лёгкий (без админа) | Полный (админ, фаза 4) |
|---|---|---|
| Запуск | LaunchAgent (macOS), автозагрузка пользователя (Windows) | LaunchDaemon + агент в контексте LoginWindow (macOS); служба SYSTEM + помощник в консольной сессии (Windows) |
| Разрешения macOS | Запись экрана + Универсальный доступ (даёт пользователь, без админа) | те же + установка демона (админ один раз) |
| Экран входа / блокировка | нет | да |
| Окна с повышенными правами, UAC (Windows) | ввод не проходит (UIPI), клиент предупреждён (`InputBlocked`, 2.6e) | да |
| Ctrl+Alt+Del | нет | да (SendSAS) |
| Автостарт до входа | нет | да |

Общая логика захвата/транспорта одна; режим определяет только «кто запускает
процесс и в какой сессии». Полный режим на Windows: служба не захватывает сама,
а запускает `rcdesk-host --session` в активной консольной сессии через
`WTSQueryUserToken` + `CreateProcessAsUser` и перезапускает при смене сессии.

Лёгкий режим реализован (2.6d), выключен по умолчанию: LaunchAgent-плист
`~/Library/LaunchAgents/app.rcdesk.agent.plist` на macOS, значение
`HKCU\Software\Microsoft\Windows\CurrentVersion\Run` на Windows —
`platform::{macos,windows}::autostart`, включается пунктом меню агента «Start
at login» или `rcdesk-host autostart on`. `launchctl` не вызывается: файл
только пишется/удаляется, эффект — со следующего входа.

## 9. Платформы

- **macOS 13+** (ScreenCaptureKit), сборки arm64 и x86_64. Подпись: пока
  self-signed сертификат с постоянным идентификатором, чтобы TCC-разрешения
  переживали пересборку; Developer ID + нотаризация — когда появится аккаунт.
- **Windows 10 1903+ и 11**, x64. WGC, Media Foundation, SendInput. Тестовый
  стенд владельца — Windows 10 x64.

## 10. Известные ограничения браузеров

- Safari: нет Keyboard Lock API → Cmd+Tab/Cmd+W/Cmd+Q остаются локальными.
  Chrome в fullscreen перехватывает их.
- Safari: Clipboard API только по жесту пользователя; синхронизация буфера —
  «по кнопке/по Cmd+V», не фоновая.
  Реализовано (2.5): копирование с хоста — `clipboard.write` с `ClipboardItem`-промисом внутри жеста Ctrl/Cmd+C;
  вставка на хост — `readText` на Ctrl/Cmd+V, Safari показывает кнопку «Вставить».
- H.264 CBP — общий знаменатель; более эффективные профили/кодеки — по
  переговорам SDP, не по умолчанию.
- Автовоспроизведение видео со звуком требует жеста; видео `muted` — нет.

## 11. Инфраструктура

VPS владельца (FastVPS, Эстония), отдельный пользователь FastPanel `rcdesk`. Docker Compose:
`rcdesk-server` (порт 8080 на localhost) и `coturn` (host-сеть). nginx FastPanel: статика
`web/dist`, прокси `/ws` и `/healthz` на 8080, TLS от панели. DNS `rcdesk.app` → VPS;
`turn.rcdesk.app` → тот же IP (без CDN-прокси). Порты: 443 (https/wss), 3478 udp/tcp и
5349 tls (TURN), диапазон relay UDP 49152–65535. Деплой — GitHub Actions по push в `main`
после зелёных гейтов (фаза 3).

Трафик через сервер — только при TURN-релее; при прямом P2P сервер видит лишь
сигналинг. Оценка: офисная работа 1080p 0.5–3 ГБ/час, видео/анимация 4–9 ГБ/час.

**Бюджет трафика (решение владельца, 2026-09-14).** Квота VPS — 10 ТБ/месяц, считается
только исходящий трафик; VPS общий с crewtally, **rcdesk отводится 5 ТБ/месяц**. Релей
через coturn расходует квоту один раз (вход от хоста не считается, выход к клиенту —
считается), то есть 5 ТБ ≈ 550–1250 часов релея видео или ≈ 1700+ часов офисной работы
в месяц; прямые P2P-сеансы квоту не тратят. Механизма учёта и отсечки на сервере пока
нет (долг D22). Реализация (под-шаг 2.4e «инфра: монитор трафика», 2026-09-14):
coturn получает `--prometheus --prometheus-address=127.0.0.1` (host-сеть, метрики на
`127.0.0.1:9641/metrics`); скрипт `infra/traffic-monitor.sh` по cron пользователя `rcdesk`
раз в 10 минут суммирует счётчики coturn `turn_total_traffic_sentb` +
`turn_total_traffic_peer_sentb` (оба направления релея выходят с VPS) и `tx_bytes`
внешнего интерфейса (`/sys/class/net/ens3/statistics/`, весь VPS), копит помесячный итог
в `~/app/traffic/<YYYY-MM>.state` (плоский `key=value` — `jq` на VPS нет; счётчики
сбрасываются при рестарте coturn/VPS, поэтому хранятся последнее значение и накопленная
сумма) и при пересечении порогов 50/80/100 % от 5 ТБ (и 90 % от 10 ТБ по интерфейсу)
шлёт уведомление один раз на порог. **Решения владельца (2026-09-14):** канал —
Telegram-бот (`TRAFFIC_TG_BOT_TOKEN`/`TRAFFIC_TG_CHAT_ID` в `~/app/.env`); на 100 % —
только уведомить, отсечка (флаг «не выдавать TURN-креды» в сигнальном сервере) — фаза 3.
Деплой копирует скрипт в `~/app/`, crontab ставится один раз вручную (`infra/README.md`).
