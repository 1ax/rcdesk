# rcdesk — Архитектура

> Документ решений. Меняется только осознанно, с записью в SLICES_LOG.md.
> Актуально на 2026-10-14 (слайс E).

## 1. Цель и границы

Удалённое управление рабочим столом macOS и Windows **из браузера** (Safari и
Chrome как минимум) с максимальной производительностью: низкая задержка, высокий
fps, аппаратное кодирование. Ориентир — Chrome Remote Desktop.

Аудитория на старте: владелец и небольшая команда (до десятков хостов). Публичный
масштаб не проектируем, но не закрываем: авторизация и сигналинг делаются так,
чтобы добавить учётки и подписи кода без переписывания.

Не делаем (пока): Linux-хост, нативные клиенты. Мобильный браузер (iOS Safari, Android Chrome) — полноценный
клиент с сенсорным вводом и экранной клавиатурой (слайс H), без отдельного приложения.

## 2. Стек и обоснование

| Слой | Выбор | Почему |
|---|---|---|
| Хост-агент | **Rust**, один код для macOS и Windows | Единственный вариант «один бинарник, нативная скорость, без рантайма» с живыми крейтами под захват, кодек, WebRTC и ввод. Go требует cgo под ScreenCaptureKit/DirectX; Electron — 200 МБ и лишний слой. |
| Захват экрана | `scap` (ScreenCaptureKit на macOS, Windows Graphics Capture на Windows); на Windows запасной **GDI** (`BitBlt`) | Единый API поверх нативных zero-copy захватов. Используется в проде (Cap.so). Если упрёмся — прямые `screencapturekit` / `windows-capture`. WGC требует Direct3D 11 у драйвера; на легаси-драйверах и в ВМ хост сам уходит на GDI (`--capture auto`, слайс 2.1). |
| Кодек, запасной | `openh264` (Cisco, программный) | Портативно, лицензионно чисто, достаточно для 1080p30 на M4/современном x64. Запасной путь, если нативный кодер не создался, и единственный вне macOS/Windows. Потолок QP 30 по умолчанию (`--max-qp`) против размытого текста. |
| Кодек, аппаратный | VideoToolbox (macOS) через `objc2-video-toolbox`; Media Foundation H.264 MFT (Windows) через `windows` (слайс 2.2) | Аппаратное кодирование без зависимости от ffmpeg. `--encoder auto`: VT на macOS; на Windows — любой MFT, аппаратный первым, программный Microsoft вторым (на стенде он быстрее и резче openh264, слайс 2.2); при ошибке создания — откат на openh264. Кодер сам конвертирует `RawFrame` в свой вход (VT и MF — NV12, openh264 — I420). |
| WebRTC на хосте | `webrtc` (webrtc-rs, порт pion) | Полный стек (ICE/DTLS/SRTP/SCTP), interceptors NACK/TWCC, API знаком по pion. Развилка на будущее: `str0m` (sans-IO, встроенный BWE), если упрёмся в управление битрейтом. |
| Ввод | `enigo` (CGEvent на macOS, SendInput на Windows) | Живой, кроссплатформенный. |
| Буфер обмена | `arboard` | Текст и изображения на обеих платформах. |
| Async/логи/ошибки | `tokio`, `tracing`, `thiserror` + `anyhow` | Стандарт. |
| Общие типы протокола | крейт `proto` + `ts-rs` | Один источник правды для Rust и TypeScript; TS-типы генерируются, не пишутся руками. |
| Веб-клиент | **TypeScript** + Vite, без UI-фреймворка (при росте UI — Preact) | Клиент — это `<video>`, canvas курсора, обработчики ввода и панель. Фреймворк не нужен. |
| Сигнальный сервер | **Rust**, `axum` + `tokio-tungstenite` | Один язык с хостом, общие типы из `proto`. Нагрузка ничтожна. |
| TURN/STUN | `coturn` в Docker | Стандарт де-факто. |
| Реверс-прокси/TLS | nginx из FastPanel на VPS владельца (как в crewtally) | Порты 80/443 на VPS уже за FastPanel; LE-сертификат выпускает панель. `.app` — зона с принудительным HTTPS (HSTS preload), что нам и нужно. Caddy — запасной вариант для чистого сервера. |
| CI | GitHub Actions: `macos-latest`, `windows-latest`, `ubuntu-latest` (web, server) | Публичный репо — без лимита минут. Deploy собирает release-бинарники хоста как артефакты (`rcdesk-host-windows-x64`, `rcdesk-host-macos-arm64`), каждый теперь содержит оба бинарника пакета — `rcdesk-host[.exe]` и `rcdesk-agent[.exe]` (2.6d): кросс-компиляции нет, openh264 собирается под MSVC. |

Версии крейтов на момент выбора (crates.io, 2026-09-11): `webrtc` 0.20.5, `str0m`
0.23.1, `scap` 0.0.8, `enigo` 0.6.1, `openh264` 0.9.8, `windows-capture` 2.0.1,
`screencapturekit` 10.0.3, `objc2-video-toolbox` 0.3.2. Точные версии фиксирует
`Cargo.lock`.

## 4. Компоненты

### 4.1 Хост-агент (`host/`)

Долгоживущий процесс пользователя (лёгкий режим) или служба (полный режим, фаза 4).
Держит WS-соединение с сигнальным сервером, по запросу клиента поднимает
`RTCPeerConnection`, публикует видеотрек и принимает data channels.

Конвейер видео: `FrameSource` → `Encoder` (принимает `RawFrame`, конверсию в
свой входной формат делает сам и ставит `captured_at` из времени захвата) →
RTP-пакетизатор webrtc-rs → сеть. Один рабочий поток на захват, один
на кодирование, транспорт на tokio. Между ними — ограниченные каналы с политикой
«держать только последний кадр» (старый кадр важнее сбросить, чем доставить).

Пейсинг: целевой fps задаётся клиентом (30/60), кадр кодируется только если
источник сообщил об изменении (SCK/WGC отдают кадры только при изменении экрана —
статичный экран стоит ~0 трафика). Ключевой кадр — по PLI/FIR от клиента и при
подключении; периодический IDR — страховка раз в `fps*60` кадров (слайс F1, было `fps*10`).

Квик-вины видеопути (слайс F, 2026-10-14; каждый с цифрой в SLICES_LOG): RTP-пейсинг в
`start_video` — кадр длиннее 32 пакетов уходит пачками по 32 с паузой 1 мс, после 30 мс остаток
без пауз (грубый таймер Windows не должен добавить больше одного кадрового интервала); VideoToolbox
берёт входные буферы из своего `CVPixelBufferPool` (IOSurface-backed), а если VT отдал больше одного
выхода за `encode()`, следующий кадр принудительно ключевой; openh264 — слайсы
`SM_SIZELIMITED_SLICE` по 8000 байт и до 4 потоков (1080p: 24.8 → 19.5 мс/кадр; слайс 1200 без
FU-A стоил +12 % битрейта); GDI — две DIB-секции по очереди, одна копия на изменённый кадр и ноль
на статичном. LTO (`thin`/`fat`) измерен и отвергнут: bench не меняется (горячий путь — C-код
openh264 и системные кодеры), `fat` лишь уменьшает бинарник 14.4 → 10.4 МБ ценой 8× времени линка.

Экран сразу после подключения (слайс 2.6f): если запрошен ключевой кадр, а новый
кадр от источника не пришёл за `SLOT_WAIT_TIMEOUT` (статичный экран), кодер-поток
перештамповывает временем «сейчас» и кодирует как ключевой последний захваченный
кадр вместо ожидания следующего изменения на экране — иначе подключившийся клиент
видит чёрный экран, пока хост не изменится.

Диагностика сеанса (слайс A, 2026-10-13): задача адаптации раз в 5 с пишет `info` «video: 5s summary»
(захвачено/закодировано/отброшено/пропущено пейсером/перезаписано, ключевые кадры, кбит/с, encode ms
avg/max, потери, REMB, текущая цель) — по `agent.log` видно, где встал видеопуть.

Мультимонитор (слайс 2.4): захват + кодер + контроллер адаптации живут в
`VideoPipeline` на один дисплей. По `control: SelectDisplay` хост поднимает новый
`VideoPipeline` для выбранного дисплея и только потом гасит старый (отказ оставляет
прежнюю трансляцию); `PeerConnection`, трек, data channels и роутер ввода не
пересоздаются, все pipeline сессии пишут в один канал `start_video` и делят один флаг
keyframe. Старый pipeline останавливается через `spawn_blocking`; `PipelineHandle::stop`
поднимает `FrameSource::stop_signal()` до `join`, и живой источник возвращает `Stopped`
в пределах 250 мс (scap: `get_next_frame_timeout` из `vendor/scap`) или одного тика
пейсера (GDI) даже на статичном экране (слайс A, 2026-10-13; раньше capture-поток SCK
висел в `get_next_frame` до следующего изменения экрана). Список дисплеев
(`control: Displays`, id/название/размер/primary) уходит клиенту при открытии `control`
и после каждого переключения; без `--display` берётся primary. На Windows список —
свой `EnumDisplayMonitors` (`platform::windows::monitors`), id = HMONITOR, как у scap.

Агент в трее (2.6c): второй бинарник, `rcdesk-agent` (macOS меню-бар / Windows трей),
поверх того же `app::run_agent`; `rcdesk-host` не меняется. Главный поток занят
собственным минимальным циклом событий (`platform::{macos,windows}::event_loop::pump`,
без winit/tao — см. §14) и меню `tray-icon`/`muda`; `run_agent` крутится на отдельном
`tokio::runtime::Runtime` (не `#[tokio::main]`), общаются через `watch<AgentStatus>` и
`mpsc::UnboundedSender<AgentCommand>` (`EndSession`). Лог — файл (`agent::paths::log_dir()`:
`~/Library/Logs/rcdesk/agent.log` / `%LOCALAPPDATA%\rcdesk\logs\agent.log`, ротация от 5 МБ)
вместо stderr; один экземпляр — лок-файл в `agent::paths::data_dir()`. На время активной
сессии хост держит систему от сна: `NSProcessInfo` activity (macOS) / `SetThreadExecutionState`
(Windows) — иначе App Nap/сон душит фоновый процесс без окон.

Постоянное устройство (3.1): при первой регистрации сервер выдаёт `device_id` + секрет,
хост хранит их в `device.json` рядом с локом (`agent::paths::data_dir()`, 0600 на Unix,
запись атомарная) и предъявляет при каждом подключении — `host_id` перестаёт меняться
при перезапусках и деплоях. Ответ сервера `unknown device` (базу пересоздали) хост
обрабатывает сам: забывает креды и тут же регистрируется заново, без ожидания backoff.
Ответ `invalid device credentials` файл НЕ трогает — это признак подделки или порчи,
в лог идёт предупреждение с путём.

### 4.2 Веб-клиент (`web/`)

Одна страница. Подключается к сигнальному серверу по WSS, получает список хостов,
устанавливает WebRTC-сессию. `<video>` с `playsinline`, `autoplay`, `muted`;
поверх — canvas локального курсора. Захват ввода: `pointermove` с
`getCoalescedEvents`, `keydown/keyup` по `event.code` (физическая клавиша, не
символ), колесо с нормализацией `deltaMode`. Pointer Lock по клику,
Keyboard Lock в Chrome в полноэкранном режиме. Оверлей статистики
(`getStats()`: fps, битрейт, RTT, jitter, потери, кодек). На приёмнике видео
`jitterBufferTarget = 0` (слайс F5): кадры рабочего стола идут нерегулярно, адаптивный буфер
Chrome (12–149 мс в живых сеансах) только добавлял задержку; ставится, если свойство есть.
Селектор дисплеев в панели
сессии появляется при двух и более дисплеях и блокируется до ответа хоста `Displays`.
Идентификатор сборки (слайс 2.6f): `build <short sha>` (`dev` вне CI), приглушённой
подписью поверх обоих экранов — чтобы вкладка, оставшаяся открытой с прошлого
деплоя, была видна на глаз, а не молча работала на старом протоколе.

«Мои компьютеры» (3.1e): на первом экране над полем PIN — список привязанных устройств
с состоянием (в сети / занят / не в сети + когда был), подключение по клику без PIN,
инлайновое переименование и удаление в два клика. Соединение с сигнальным сервером
теперь ОДНО на вкладку и живёт дольше сеанса: сервер помнит владельца только в пределах
сокета, поэтому привязка при входе по PIN возможна лишь на том же соединении. Список
обновляется раз в 10 с и при возврате фокуса на вкладку; обрыв связи с сервером виден
надписью, клиент сам переподключается (3.5a). Вход по PIN остаётся — это первая привязка и
разовый доступ к чужой машине.

**Мобильный клиент (слайс H).** Касания (`pointerType === "touch"`) не идут мышиным путём, а попадают в
распознаватель жестов `touchInput.ts` (чистая логика, без DOM). Режим по умолчанию — **трекпад**: палец ведёт
виртуальный курсор относительно (1:1 к пикселям отображаемого кадра), тап — клик, долгое нажатие — зажатая левая
(перетаскивание), тап двумя — правая, ведение двумя — колесо (`WheelAccumulator` копит пиксели и шлёт только
целые линии: хост округляет `wheel`), щипок — масштаб слоя видео 1x–4x (`viewport.ts`, `#zoom-layer` с CSS-трансформом;
`mapPointer` работает через `getBoundingClientRect`, поэтому масштаб учитывается сам). Вьюпорт едет за курсором у
края. **Прямой режим** (кнопка «Трекпад/Касание», `rcdesk.touch-mode`): тап кликает в точке касания, ведение
панорамирует, долгое нажатие — правая. Курсор на сенсоре рисуется `<img>` поверх видео из той же формы, что хост шлёт
для CSS-курсора. На видео `touch-action: none`, на экране сеанса тоже — иначе браузер забирает жест и шлёт
`pointercancel` с зажатой кнопкой. Экранная клавиатура — кнопка «Клавиатура»: скрытое поле без автокоррекции,
текст снимается дифом содержимого на `input` (пробел-страж в начале делает Backspace на пустом поле видимым),
Enter/Backspace уходят как `Key`, остальное — `Text` (§7) или, для хоста < 0.1.8, через таблицу символ → физическая
клавиша (`charKeys.ts`: US и ЙЦУКЕН). Строка спецклавиш над клавиатурой: Esc, Tab, стрелки, Del и липкие
Ctrl/Alt/Cmd|Win/Shift (тап — до следующей клавиши, второй — защёлка); с модификатором буква уходит как код клавиши,
поэтому Ctrl+«с» = Ctrl+C. Положение строки и высота экрана сеанса при поднятой клавиатуре — по `visualViewport`.
Манифест (`display: standalone`) без service worker: на iPhone нет Fullscreen API для `div`, запуск с домашнего
экрана — единственный «полный экран»; Screen Wake Lock держится с первого кадра до конца сеанса.

### 4.3 Сигнальный сервер (`server/`)

Хосты регистрируются по WSS с `device_id` + секретом устройства; клиенты
подключаются по WSS. Сервер только пересылает SDP/ICE между парами и отдаёт
владельцу список его устройств. Состояние двухслойное (3.1): сиюминутное —
в памяти (`registry.rs`: живые соединения, PIN-индекс, сессии), постоянное —
в SQLite (`db.rs`: `devices`, `owners`, `ownership`; схема версионируется
`PRAGMA user_version`, файл — в томе `/data`, путь из `RCDESK_DB_PATH`).
Опознание устройств — `devices.rs`, владельцев — `owners.rs`; секреты и токены
хранятся только SHA-256-хешем. Выдаёт короткоживущие TURN-креды (coturn REST API, HMAC).
TURN-креды выдаются в `Joined` и `PeerJoined`: хост берёт свежие на каждый сеанс (2.6b);
`Registered` несёт только STUN (слайс B — неаутентифицированному хосту креды не выдаются).

**Лимиты и живость (слайс B, 2026-10-13).** Кадр WebSocket ≤ 64 КиБ (`ws::MAX_MESSAGE_BYTES`);
исходящая очередь соединения — bounded-канал на 256 сообщений с «рубильником» (`registry::Tx`):
переполнение или запись в сокет дольше 10 с закрывают соединение получателя штатно (цикл чтения
выходит и делает уборку). Сервер шлёт Ping раз в 30 с и закрывает соединение без кадров 90 с
(`app::Liveness`). Три ведра по IP (`ip_limit::IpLimiter`): неверный PIN 10/мин, новые
анонимные владельцы 20/мин, новые устройства 10 за 10 мин — сверх лимита `too many attempts`.
Ключ ведра для IPv6 — префикс /64 (слайс D); плюс одно общее ведро на все отказы `Join`
(`ip_limit::GlobalLimiter`, 300 залпом, 1 токен в 2 с).
Устройства без владельца, не регистрировавшиеся 30 дней, удаляются суточной задачей (онлайн —
нет). SQLite: WAL + `synchronous=NORMAL` + `busy_timeout` 2 с. `/healthz` делает `SELECT 1` и
берёт мьютекс реестра, иначе 503 (деплой сверяет тело `ok`). Имя хоста и алиас ≤ 64 символов.
Одно клиентское соединение — один сеанс (`already in session`).

### 4.4 Общие типы (`proto/`)

Все сообщения — `serde` структуры с `#[derive(TS)]`; `cargo test -p proto`
генерирует `web/src/generated/*.ts`, CI проверяет, что сгенерированное совпадает
с закоммиченным. Никакого кода с логикой.

## 5. Транспорт: WebRTC

- **Видео:** один трек, H.264, `packetization-mode=1`, профиль
  Constrained Baseline `42e01f` (единственный, который гарантированно аппаратно
  декодируют и Safari, и Chrome). Позже — переговоры High `640032` для Chrome и
  AV1 как опция. Без B-кадров, без открытых GOP, `max-fr`/`max-fs` не ограничиваем.
- **Data channels** (SCTP):
  - `input` — надёжный, упорядоченный: клавиши, кнопки мыши, колесо; буфер обмена клиент → хост
    (`ClipboardText` в одном потоке с клавишами: буфер хоста обновлён строго до следующего Cmd+V).
  - `pointer` — `ordered: false, maxRetransmits: 0`: движения мыши (потерянное
    движение не важно, следующее его заменит).
  - `control` — надёжный: буфер обмена хост → клиент, смена монитора, качество, курсор, пинг, статус ввода,
    предупреждение об окне с повышенными правами (Windows, `InputBlocked`, 2.6e).
  - `file` — надёжный, чанки 64 КиБ (≤ `maxMessageSize`) с backpressure (браузер — `bufferedAmount` 1 МиБ/256 КиБ,
    хост — `outstanding_bytes` > 1 МиБ). Протокол — `proto::file` (слайс 3.4): JSON `start`/`end`/`abort`/`saved`/
    `offer`/`fetch`, чанки — бинарные сообщения без заголовка; в каждую сторону одна передача за раз, чанк относится к
    последнему `start` от той же стороны; id клиента с 1, хоста с `0x8000_0000`. На хосте канал обслуживает своя
    задача `files::run`, мимо `handle_session_event`.
    **Решения владельца 2026-10-09:** клиент → хост — кнопка «Отправить файлы» и перетаскивание на видео, файлы
    в системные «Загрузки» хоста (Windows — `FOLDERID_Downloads`), запись в `.rcdesk-part` + имя-заглушка через
    `create_new`, чистка имени и суффикс `(N)`, в буфер хоста не кладутся; хост → клиент — файлы, скопированные в
    буфер хоста (Cmd/Ctrl+C в Finder/Проводнике внутри сеанса): наблюдатель буфера отдаёт список файлов вместо
    текста, клиент показывает «Скачать (N)», файл собирается в `Blob` (лимит 2 ГиБ на скачивание); папки не
    поддерживаются (пропускаются с сообщением). Скачивание требует включённых и буфера, и файлов; `--no-files`
    отключает обе стороны, клиент узнаёт из `HostInfo.files_enabled`.
- **RTP-время видео:** отметка кадра = реальное время захвата (транспорт пакетизирует сам:
  `TrackLocalStaticRTP` + `Packetizer`, `skip_samples` на интервал между захватами). Фиксированный
  шаг `1/fps` недопустим: кадры идут только при изменении экрана, и Chrome копил ~850 мс в jitter-буфере.
- **Кодирование сообщений:** JSON (MVP; типы из `proto`). Если измерение покажет
  накладные расходы на `pointer` — компактный бинарный формат, решение фазы 2.
- **Управление битрейтом (слайс 2.3):** контроллер на хосте (`host/src/adapt`), тик раз в
  секунду, входы — **REMB** от браузера (оценка его receive-side GCC, ограничена ~1.5× принятого
  и растёт ~8 %/с; сигнал перегрузки только когда канал нагружен — отправлено ≥ 80 % цели — и REMB
  ниже отправленного два тика подряд и при этом не растёт — растущий REMB просто догоняет поток;
  иначе на статичном экране или на старте видео он режет цель без причины),
  **доля потерь из RTCP RR** (свежее `LOSS_FRESH` 3 с, иначе ноль — слайс F1; > 10 % — срез; при отсутствии сигналов перегрузки и потерь < 2 % —
  пробинг +10 %/с, единственный путь вверх) и **перезапись слота захвата** (кадр пришёл, пока кодер
  занят предыдущим, ≥ 2 за тик — ступень fps вниз; пять чистых тиков — вверх).
  Порядок «сначала fps, потом битрейт» — через бюджет кадра (0.02 бит/пиксель): при низком
  битрейте fps опускается раньше, чем картинка станет мылом. Разрешение не меняется (долг
  на будущее). Выходы: `Encoder::set_rate` (без пересоздания кодера) и пейсинг fps в
  конвейере до кодера. `--no-adapt` отключает для замеров «до/после».
  **Пресеты (слайс 3.5e)** — `ControlMessage::SetQuality` от клиента меняет политику контроллера
  на лету: «Авто» — как выше; «Чёткость» — потолок 15 fps и бюджет 0.06 бит/пиксель (fps жертвуется
  раньше качества кадра); «Плавность» — пол 15 fps и бюджет 0.01 (режется битрейт, а не fps). Смена
  пресета стартует с потолка fps нового пресета; пресет живёт в сеансе и переживает смену дисплея,
  клиент помнит выбор по устройству в `localStorage`.
  **TWCC на хосте не включён намеренно:** `register_default_interceptors` ставит TWCC
  только на приём; если добавить расширение в исходящие пакеты, Chrome перестанет слать
  REMB и оценку (GCC) придётся писать самим — развилка на будущее (или `str0m`).
  **abs-send-time в каждом видеопакете (D76, задача 010):** хост регистрирует
  `http://www.webrtc.org/experiments/rtp-hdrext/abs-send-time` и ставит время отправки после
  паузы пейсинга. Без него receive-side оценщик libwebrtc (Chrome и Firefox) считает задержку
  по RTP-меткам захвата, принимает задержку кодера и пейсинга за очередь и держит REMB на полу
  (5–17 кбит/с, логи 0.1.15–0.2.1). TWCC это не включает: REMB браузер шлёт по-прежнему.
- **ICE:** STUN + TURN (udp/tcp/tls на 443 для корпоративных сетей).
- **Шифрование:** DTLS-SRTP (WebRTC), DTLS для SCTP. Сервер видит только сигналинг.

## 6. Сигналинг и авторизация

Транспорт — WSS, сообщения JSON из `proto::signal`.

**MVP (фаза 1):** хост при запуске показывает 6-значный PIN, клиент вводит PIN,
сервер сводит пару. PIN живёт до первого подключения или 10 минут.

**Слайс 3.1 (сделано).** Устройство получает постоянный `device_id` + секрет:
`HostRegister { name, device }` → сервер сверяет SHA-256-хеш секрета и возвращает
тот же `host_id`, при первой регистрации выдаёт креды в `Registered.device`. Владелец
(браузер) получает постоянный токен: `ClientAuth { token }` → `Authenticated { token,
devices }`, в БД — только хеш. Вход по PIN привязывает устройство к владельцу
(`ownership`), дальше клиент подключается сообщением `ConnectDevice { device_id }`
без PIN; список отдаётся с состоянием `online`/`busy` из реестра соединений,
`RenameDevice`/`ForgetDevice` его правят. Повторная регистрация того же устройства
вытесняет старое соединение и закрывает его сеанс.

**Решения слайса 3.1 (владелец, 2026-09-20).** Учёток (email/пароль, magic link)
пока НЕТ: владелец — это браузер с bearer-токеном в `localStorage`. Потеря токена =
потеря списка, устройства перепривязываются по PIN за минуту; за это куплен слайс без
почтового сервера и хранения паролей. Привязанный владелец подключается без
подтверждения на хосте — как TeamViewer с сохранённым паролем; окно «разрешить?» на
хосте — отдельная работа позже. Бэкап БД не делаем: потеря базы переживается штатно
(сервер отвечает `unknown device`, хост сам перерегистрируется, владелец заново
привязывает по PIN), а `sqlite3` в образе и cron на VPS ради этого не окупаются.
Пересмотреть в 3.2, где появятся пароли доступа.

**Жизнь сеанса (слайс 3.5).** Сеанс P2P: сигналинг нужен только для установки, поэтому
обрыв WS (рестарт сервера при деплое, сбой сети) сеанс **не** рвёт — сервер при закрытии
сокета не шлёт `Bye` второй стороне, хост держит сеанс в `SessionSlot` поверх цикла
реконнекта (весь handshake хоста — TCP, WS, `Hello`, `HostRegister`, `Registered` — под таймаутом
30 с, `signaling::CONNECT_TIMEOUT`, слайс A), клиент переподключает WS с backoff 1–30 с. При перерегистрации хост называет
живой сеанс (`HostRegister.session_id`, 3.2a): сервер переподвешивает известную сессию на новое
соединение, неизвестную держит «отвязанной» (устройство занято, пересылать некому) до `Bye`
хоста; хост шлёт `Bye` при любом локальном конце сеанса. WebRTC `disconnected` — не конец: обе стороны ждут 15 с;
не вернулось или `failed` — клиент сам подключается заново к тому же устройству
(`Joined.device_id`, до 5 попыток, 1–16 с). Намеренный конец — `Bye`, закрытие канала
`control` (хост гасит сеанс сразу) или `pagehide`. События транспорта несут тег
`PeerSession`, чтобы запоздавшее событие старого PC не погасило новый сеанс.

**Пароль доступа к хосту (слайс 3.2, решения владельца 2026-09-22).** Протокол — OPAQUE:
`opaque-ke` 4.0 на хосте и `@serenity-kit/opaque` в браузере (та же библиотека, собранная в
WASM), шифронабор ristretto255 + TripleDH/SHA-512 + argon2id (m = 2^16 KiB, t = 3, p = 4 —
дефолт serenity-kit, должен совпадать байт в байт), идентификаторы и контекст пустые,
`credential_identifier` = `rcdesk-owner`. Альтернативы отвергнуты: RustCrypto `spake2` —
вариант python-spake2 на Ed25519, не RFC 9382, без подтверждения ключа и без JS-пары;
`pakery-spake2` следует RFC, но свежий и с одним мейнтейнером; своя SPAKE2 на
`@noble/curves` + `p256` — собственный криптокод без аудита. Хост хранит `ServerSetup` и
`RegistrationRecord` в `access.json` рядом с `device.json` (0600, атомарная запись) и не
знает пароль после регистрации; задаётся только через CLI `rcdesk-host password set|clear|
status` на машине хоста (меню трея текст вводить не умеет, GUI-диалог не заводим). Пароль
обязателен и при входе по PIN (PIN виден на экране хоста и в трее — это привязка, не
секрет), в браузере не запоминается (иначе возвращается D33). Поток: `PeerJoined` → хост с
паролем шлёт `AuthRequired`, три сообщения OPAQUE идут через сервер по `session_id` (сервер
только ретранслирует), `start_session` — только после успешного `ServerLogin::finish`;
провал — `AuthFailed`; каждый `PakeStart` — попытка (хосту она стоит одной OPRF-оценки, офлайн-
перебор без неё невозможен), после пяти хост ставит паузу перед следующей (5→60 с) и на попытку
раньше срока отвечает `AuthFailed { retry_after }`, не запуская протокол; сама попытка после паузы
выполняется, успех сбрасывает счётчик (цикл сигналинга блокировать нельзя, поэтому только отказ
по времени). Отпечатки DTLS привязываются к общему
`session_key`: хост кладёт в `Offer` HMAC от своего `a=fingerprint:` из SDP, клиент сверяет
до `setRemoteDescription`; клиент — то же в `Answer`, хост сверяет до `set_answer`
(публичного API для удалённого сертификата в `webrtc` 0.20 нет, свой сертификат задавать
не нужно — отпечатки и так в SDP). Без пароля на хосте поведение прежнее.

**Лимит подбора PIN (слайс 3.6a).** Сервер считает неверные PIN по IP клиента (`X-Real-IP` от nginx,
иначе адрес сокета): ведро на 10 попыток, пополнение одна в минуту; сверх лимита `Join` получает
`too many attempts` без проверки PIN. Удачный вход попытку не тратит.
Слайс B обобщил ведро в `IpLimiter` и добавил ещё два: создание анонимного владельца
(`ClientAuth` с неизвестным/пустым токеном, 20/мин) и регистрация нового устройства
(`HostRegister` без кредов, 10 за 10 мин); известные токены и устройства лимит не тратят.
`X-Real-IP` сервер доверяет как раньше: в Docker за bridge-сетью nginx и трафик через
coturn-релей приходят с одного адреса шлюза, различить их по пиру нельзя — подделку через релей
закрывает `--denied-peer-ip` у coturn на localhost и внутренние диапазоны (слайс C; внешний IP VPS не
запрещён — при релее с обеих сторон пир это relay-адрес самого coturn, иначе `ChannelBind` → 403). Проверка `Origin` на `/ws` не делается
сознательно: cookie нет, токен владельца живёт в `localStorage` и шлётся сообщением, поэтому
чужой сайт из браузера жертвы ничего не получает. Graceful shutdown не делается: WAL не теряет
закоммиченное при SIGKILL, клиенты переподключаются с backoff.

**Ротация и TTL PIN (слайс D, 2026-10-13, D44).** PIN хоста меняется после каждого успешного
`Join` и по истечении 10 минут (`app::Liveness.pin_ttl`): сервер шлёт хосту `PinChanged { pin }`,
хост переиздаёт статус с новым кодом (трей, `serve`, `pin.txt`). Просроченный PIN в `join` равен
`unknown pin`; фоновая задача `spawn_pin_rotation` раз в `ttl/10` ротирует просроченные. Ротация
включается только для хоста, заявившего `HostRegister.pin_rotation: true` (агент ≥ 0.1.5): старый
агент без поля живёт со статичным PIN, как раньше, и не показывает устаревший код. В сеансе PIN
ротируется так же. Любой отказ `join` (`unknown pin`, `host busy`, `already in session`) тратит
токен IP-ведра и общего ведра — иначе ответ «занят» бесплатно подтверждал верный PIN. Ключ
IP-ведра для IPv6 — /64 (IPv4-mapped сводится к IPv4). Общее ведро — второй контур против
распределённого перебора: 300 отказов залпом, затем 1 в 2 с (~43 тыс./сутки на сервер против
10^6 кодов); при его исчерпании `Join` отвечает `too many attempts` и верному PIN, привязанные
устройства идут через `ConnectDevice` без PIN. `Join` не тратит ничего при успехе.

**Привязка DTLS и устойчивость клиента (слайс E, 2026-10-14).** Дыра аудита: клиент сверял тег
`Offer.auth` только если в этом же сеансе прошёл OPAQUE, поэтому сервер-в-середине, не переславший
`AuthRequired` и приславший `Offer` с `auth: null`, обходил привязку. Теперь клиент помнит по
`device_id` в `localStorage` (`hostTrust.ts`, ключ `rcdesk.authRequired.<id>`), что хост однажды
потребовал пароль, и отклоняет `Offer` без пройденного входа (`Bye` + текст с подсказкой); флаг
снимается кнопкой «Удалить» устройство — после снятия пароля на хосте владелец удаляет устройство
из списка и привязывает заново по PIN. TOFU самого отпечатка не делаем: при пароле его заменяет
HMAC, без пароля сервер и так посредник. Отпечаток из SDP на обеих сторонах — все строки
`a=fingerprint` (session-level и m-секции), расхождение между ними = «отпечатка нет» = отказ: по
RFC 8122 медиа-уровень перекрывает сессионный, а проверка одной первой строки пропускала подмену в
m-секции (Chrome применил бы её). Ошибка `set_answer` на хосте завершает сеанс с `Bye`, а не
оставляет его висеть. Клиент сверяет `session_id` в `offer`/`ice`, после каждого `await`
проверяет, что сеанс не сменился, колбэки `PeerSession` игнорируют устаревший PC, повторный
`joined` при живом сеансе сначала закрывает старый; попытка восстановления ждёт `joined`/`error`
не дольше 15 с (`RECOVERY_RESPONSE_TIMEOUT_MS`), иначе идёт следующая по расписанию.
Серверные сообщения в `SignalingClient` диспатчатся под префиксом `msg:`, чтобы серверное
`{"type":"close"}` не подделывало закрытие сокета. Приём файлов сверяет `size` каждого `start` с
остатком бюджета оффера (не только сумму оффера в `fetch`). Синхронизация буфера обмена —
чекбокс «Буфер обмена» в панели сеанса, по умолчанию **выключена** и запоминается на браузер
(`rcdesk.clipboardSync`): автосинхронизация шлёт на хост каждое локальное копирование, включая
пароли из менеджера (решение владельца 2026-10-14); при записи с хоста показывается заметка
«Буфер обновлён с хоста». meta-CSP в `index.html` не делаем: CSP enforcing уже в nginx (слайс C,
`infra/nginx/rcdesk.app.conf`), копия в meta требовала бы синхронизации, а `frame-ancestors` в
meta не работает.

**Причина в `Bye` (слайс 4.6b).** Необязательное поле `reason` (`ByeReason`, сейчас один вариант
`display_unavailable`): хост ставит его, когда дисплей так и не появился после пробуждения, сервер пересылает как
есть, клиент завершает сеанс текстом «Экран хоста недоступен: дисплей спит или отключён» без автопопыток. Без поля
JSON прежний — старые стороны совместимы в обе стороны.

**Аккаунт и кабинет (слайс 3.7, решения владельца 2026-10-12).** Аккаунт — тот же владелец (`owner_id`), к которому
добавлены passkey и несколько браузеров; почты и паролей нет, аккаунт необязателен. Токены браузеров — в
`owner_tokens` (хеш, User-Agent, создан, последний вход), владелец видит их в кабинете и отзывает
(`ListBrowsers`/`RevokeBrowser`/`SignOut`); отозванный токен теряет доступ на следующем же запросе (`require_owner`).
Passkey — `webauthn-rs` 0.5.5 c фичей `conditional-ui`: регистрация к текущему владельцу (`residentKey: required` в
опциях для браузера), вход без логина (discoverable) выдаёт браузеру новый токен владельца. Церемонии идут по тому же
WS (`PasskeyRegister*`, `PasskeyLogin*`, `options`/`credential` — JSON webauthn-rs строкой, proto о нём не знает),
состояние — в памяти соединения. При входе анонимный владелец браузера (без passkey) вливается в аккаунт и удаляется;
владелец-аккаунт не трогается. RP ID — `rcdesk.app` (`RCDESK_WEBAUTHN_RP_ID`/`RCDESK_WEBAUTHN_ORIGIN`, локально
`localhost`). Общий доступ команде к компьютерам — следующий шаг.

**Учётка почта + пароль (слайс 3.8, решение владельца 2026-10-15).** Пересматривает решение 3.1 «без почты и
паролей»: passkey не всем удобен (Windows без Hello, другие браузеры). Логин — почта (trim + lowercase), пароль
8–128 символов, хеш argon2id с параметрами по умолчанию (`Argon2::default()`), в таблице `accounts` (схема v4,
`owner_id` → почта UNIQUE + хеш). Регистрация и сброс — один механизм: `EmailCodeRequest` шлёт 6-значный код
(хранится в памяти сервера, TTL 10 мин, 5 попыток, не чаще раза в минуту и 5 в час на адрес, ответ одинаковый
независимо от того, есть ли аккаунт), затем `EmailCodeConfirm { email, code, password }`: почта новая — привязывается
к текущему владельцу соединения (его устройства остаются), почта есть — это сброс пароля, все браузеры аккаунта
выкидываются, анонимный владелец соединения вливается, как при входе по passkey. Вход — `PasswordLogin`, ответ на
неверную почту и неверный пароль одинаков (`wrong email or password`, verify против фиктивного хеша). Лимиты IP:
выдача кодов 5 / 10 мин, неверный пароль или код 10 / мин. Аккаунт по-прежнему необязателен, passkey остаётся;
анонимный владелец = без passkey и без почты. Отправка писем — трейт `Mailer` (`mail.rs`): `RCDESK_MAIL=log` пишет
код в лог (локальная разработка), `smtp` — `SmtpMailer` (3.8b: `RCDESK_SMTP_HOST/PORT/USER/PASSWORD`, `RCDESK_MAIL_FROM`,
по умолчанию Resend и `rcdesk <noreply@rcdesk.app>`; без пароля сервер не стартует), пусто — почта выключена
(`email unavailable`). Ключ Resend `rcdesk-server-smtp` — только отправка, только домен `rcdesk.app`.

Смена почты вошедшего аккаунта — `EmailChange { email, code, password }` (код — обычным `EmailCodeRequest` на НОВЫЙ адрес,
пароль — ТЕКУЩИЙ; пароль проверяется до кода, чтобы неверный пароль не сжигал код). Ответ — `Account` с новой почтой;
на СТАРЫЙ адрес уходит уведомление (`Mailer::send_email_changed`, сбой отправки только в лог и не откатывает смену).
Токены и сессии не трогаются. Ошибки: `no account`, `same email`, `wrong password`, `wrong code`, `email taken`.

`EmailCodeConfirm` несёт `purpose: Option<EmailCodePurpose { Register, Reset }>` — намерение клиента (экран «Регистрация» /
«Сброс пароля», «Смена пароля»). Сервер сверяет его с наличием аккаунта после проверки кода и до argon2: `Reset` без
аккаунта с такой почтой — `no such account` (ничего не создаётся), `Register` при занятой почте — `email taken` (пароль
чужого аккаунта не трогается, переключения нет). `None` (поле отсутствует, вкладка старой версии) — прежнее поведение:
решает наличие аккаунта.

## 7. Ввод

Клиент шлёт `event.code` (например `KeyA`, `MetaLeft`) и состояние модификаторов;
хост переводит в платформенный виртуальный код (macOS — kVK_*, Windows — VK_*).
Раскладка символов — задача хоста, как при физической клавиатуре. Для текста,
который браузер не может выразить кодом (IME, вставка), — отдельное сообщение
`Text { string }` → `enigo.text()`.

Координаты мыши — нормализованные `[0,1]` относительно транслируемого монитора, хост
масштабирует их в прямоугольник этого монитора в глобальных координатах ОС
(`input::CaptureRect` из `capture::DisplayInfo`: точки CGEvent на macOS, физические
пиксели виртуального экрана на Windows) — не зависит от HiDPI и масштаба видео. На
Windows абсолютное перемещение идёт своим `SendInput` с `MOUSEEVENTF_VIRTUALDESK`
(`platform::windows::mouse`): `enigo` нормализует только по primary-монитору. Курсор
рисуется локально в клиенте по форме, присланной хостом (`control: CursorShape`),
в видео курсор не попадает — экономия битрейта и нулевая задержка курсора.

**Раскладка хоста (слайс 4.6c/d).** Клиент шлёт физические коды, поэтому Alt+Shift с Windows-клиента доходит до Mac как
Option+Shift и раскладку не меняет. Хост macOS переключает включённые клавиатурные источники ввода по кругу сам —
Text Input Sources (`TISSelectInputSource`, фреймворк Carbon, без новых крейтов; работает из фонового потока, спайк
2026-10-12) по `ControlMessage::SwitchInputSource` и сообщает метку `InputSource { label }` (`RU`/`EN`, первый язык
источника) при открытии `control`, после переключения и при смене на самом Mac (опрос 500 мс). `HostInfo.input_source_available`
— только реальный macOS-хост с вводом. Клиент: одиночное Alt+Shift (по отпусканию первой клавиши, без других клавиш,
`layoutChord.ts`) для macOS-хоста шлёт команду, сами клавиши уходят как раньше; кнопка с меткой в панели сеанса.
Windows-хост обрабатывает пересланное Alt+Shift сам.

**Спящий дисплей (слайс 4.6a).** Пока дисплей Mac спит, SCK не видит ни одного экрана. `start_session` объявляет
активность пользователя (`IOPMAssertionDeclareUserActivity`, как конкуренты) и ждёт дисплей до 5 с с шагом 250 мс;
`SessionActivity` держит `IdleDisplaySleepDisabled` весь сеанс. Windows — no-op.

Если инжектор ввода не поднялся (macOS без «Универсального доступа», `serve --no-input`), сеанс не
гаснет: хост подставляет `NoopInjector` и при открытии `control` шлёт `InputStatus { available: false,
reason }`, клиент не цепляет ввод и показывает `Только просмотр: <причина>` (2.5a, D26). Статус определяется
на старте сессии; после выдачи разрешения достаточно переподключиться.

**Текст строкой (слайс H2).** `InputMessage::Text { text }` по каналу `input` — для символов, которые клиент не
может выразить физическим кодом: экранная клавиатура телефона отдаёт пустой `code` (iOS) или `keyCode 229`
(Android). Хост вводит строку Unicode-путём мимо раскладки: macOS — `enigo.text()`
(`CGEventKeyboardSetUnicodeString`), Windows — `SendInput` с `KEYEVENTF_UNICODE` по UTF-16 единицам одним вызовом на
всю строку (`platform::windows::keyboard::send_unicode`). Лимит `MAX_TEXT_BYTES` 4096, в лог — только длина.
Управляющие клавиши по-прежнему `Key`. Хост ≤ 0.1.7 сообщение отбрасывает с `warn`, сеанс не рвётся.

## 8. Два режима хоста

| | Лёгкий (без админа) | Полный (админ, фаза 4) |
|---|---|---|
| Запуск | LaunchAgent (macOS), автозагрузка пользователя (Windows) | один системный LaunchAgent с `LimitLoadToSessionType = [Aqua, LoginWindow]` (macOS, D51); служба SYSTEM + помощник в консольной сессии (Windows) |
| Разрешения macOS | Запись экрана + Универсальный доступ (даёт пользователь, без админа) | те же + установка демона (админ один раз) |
| Экран входа / блокировка | блокировка в сеансе — да на macOS (4.2a, T3) | цель; на Windows — долг 4.1b; на macOS экран входа — ввод доходит (D51 решён 2026-10-21: секция `__CGPreLoginApp` + грант TCC), полный режим: `rcdesk-host fullmode install` (D51) |
| Окна с повышенными правами, UAC (Windows) | ввод не проходит (UIPI), клиент предупреждён (`InputBlocked`, 2.6e) | окна администратора — да (4.1a); UAC на secure desktop — долг 4.1b |
| Ctrl+Alt+Del | нет | цель (SendSAS); на Windows — долг 4.1c |
| Автостарт до входа | нет | да (Windows, 4.1a; macOS — системный LaunchAgent, D51) |

Общая логика захвата/транспорта одна; режим определяет только «кто запускает
процесс и в какой сессии». Полный режим на Windows (слайс 4.1a, решения владельца
2026-10-10): служба `rcdesk` (LocalSystem, подкоманды `rcdesk-host service …` того же
exe, SCM на `windows` 0.61) не захватывает сама, а раз в секунду опрашивает
`WTSGetActiveConsoleSessionId` и держит в активной консольной сессии помощника
`rcdesk-host serve --machine`. Помощник запускается **с токеном SYSTEM со сменённым
`TokenSessionId`** (`DuplicateTokenEx` → `SetTokenInformation` → `CreateProcessAsUserW`
на `winsta0\default`), а не с токеном пользователя (`WTSQueryUserToken`): тот имеет
уровень целостности ниже окон администратора (UIPI остаётся) и недоступен на экране
входа, где пользователя нет. Помощник в Job object с `KILL_ON_JOB_CLOSE`, перезапуск
при выходе с backoff 1–30 с (сброс после 60 с жизни), при смене консольной сессии —
убить и запустить в новой. Данные машины — `%ProgramData%\rcdesk` под защищённым
DACL (SYSTEM + Administrators); `service install` переносит туда `device.json` и
`access.json` пользователя-установщика, устройство не меняется. Если каталог уже
существует и его владелец не SYSTEM и не Administrators (либо это symlink/junction),
установка отказывает с просьбой удалить каталог (слайс G, аудит H-H2): `%ProgramData%`
по умолчанию даёт Users право создавать подкаталоги, а `create_dir_all` на существующем
каталоге — no-op, и не-админ остался бы владельцем с неявным WRITE_DAC. Файлы в
машинном режиме помощник пишет от SYSTEM, а не под токеном пользователя — долг D61
(имперсонация на время файловых операций, нужен стенд). Трея в полном режиме
нет (меню от SYSTEM — путь к повышению прав), `rcdesk-agent` при работающей службе
выходит, PIN — `service status` (`pin.txt`). Пользовательские папки (принятые файлы →
«Загрузки») помощник берёт по токену пользователя консольной сессии (4.1d).
Переключение на рабочий стол `Winlogon` (UAC, экран блокировки/входа) и Ctrl+Alt+Del
(SendSAS) — не сделаны, долги 4.1b/4.1c.

Лёгкий режим реализован (2.6d), выключен по умолчанию: LaunchAgent-плист
`~/Library/LaunchAgents/app.rcdesk.agent.plist` на macOS, значение
`HKCU\Software\Microsoft\Windows\CurrentVersion\Run` на Windows —
`platform::{macos,windows}::autostart`, включается пунктом меню агента «Start
at login» или `rcdesk-host autostart on`. `launchctl` не вызывается: файл
только пишется/удаляется, эффект — со следующего входа.

Полный режим macOS (D51, решения владельца 2026-10-21): один системный LaunchAgent
`/Library/LaunchAgents/app.rcdesk.agent.plist` (`LimitLoadToSessionType = [Aqua, LoginWindow]`,
`KeepAlive { SuccessfulExit = false }`), ставится только командой `sudo rcdesk-host fullmode install`
(`platform::macos::fullmode`, чистая логика — `fullmode.rs`). launchd поднимает из него два инстанса
одного `rcdesk-agent`: роль «сеанс» в GUI-сеансе (трей, шторка, обновления — всё как в лёгком режиме)
и роль «экран входа» в сеансе loginwindow от root (без трея, шторки и обновлений: `osascript … with
administrator privileges` установщика там невозможен). Состояние (`device.json`, `access.json`) общее —
машинный каталог `/Library/Application Support/rcdesk` (root:admin, `02770`, файлы `0660`), иначе у ролей
разошёлся бы `host_id`, а сервер вытесняет предыдущее соединение того же `host_id` (пинг-понг). Арбитраж —
одновременно подключён один инстанс: роль «экран входа» служит, только пока владелец `/dev/console`
— root (вошедшего пользователя нет) и свободен машинный лок регистрации (`registration.lock`); при
появлении пользователя выходит с кодом 3 (под `KeepAlive{SuccessfulExit=false}` launchd перезапускает
его в режим ожидания); сеансовая роль при занятом локе ждёт его до 10 с (передача без вытеснения на
сервере). Обновления — только в сеансовой роли. Пользовательский автозапуск 2.6d при установленном
полном режиме выключен гейтом (`autostart on|restore` — no-op, иначе `postinstall` pkg создавал бы
второй plist с той же меткой), `install` его снимает. Ограничение: после перезагрузки первым
идёт экран разблокировки FileVault (нет сети и агентов) — доступ только после выхода из системы.

**Шторка (слайс 4.2c, только macOS-агент).** Клиент кнопкой «Шторка» шлёт `ControlMessage::SetCurtain { on }`, хост
отвечает `CurtainStatus { on, reason }`; `HostInfo.curtain_available` — только `rcdesk-agent` на macOS (трейт
`curtain::Curtain` в `HostContext`, реализация `platform::macos::curtain`, вызовы маршалятся в главный поток агента).
Показ: чёрные `NSWindow` на уровне `CGShieldingWindowLevel` на всех экранах, CGWindowID окон исключаются из захвата
(перезапуск конвейера SCK с `exclude_windows`), локальный ввод глушит активный `CGEventTap` — проходят только события с
`EventSourceUserData = enigo::EVENT_MARKER` (наша инъекция). Окно НЕ `opaque` (чёрный 99 %): непрозрачное окно на весь
экран macOS считает перекрывающим, приложения под ним перестают рисоваться и видео застывает (фикс `db6039e`). Конец
сеанса со шторкой — сначала блокировка экрана (Ctrl+Cmd+Q с меткой, ожидание `CGSSessionScreenIsLocked`), потом снятие
шторки; если блокировка не подтвердилась, шторка остаётся (слайс G), следующий сеанс берёт её окна через
`Curtain::shown()` в исключение захвата и сразу шлёт клиенту `CurtainStatus { on: true }` — снять можно кнопкой.
Windows — долг D52.

## 9. Платформы

- **macOS 13+** (ScreenCaptureKit), сборки arm64 и x86_64. Поставка — бандл
  `rcdesk.app` (`app.rcdesk.agent`) в `rcdesk-macos.pkg`, подписан самоподписанным
  сертификатом (ключ — секреты GitHub `MACOS_SIGN_P12*`, копия у владельца): DR =
  идентификатор + лист сертификата, поэтому TCC-разрешения переживают обновление;
  без hardened runtime. Developer ID + нотаризация — когда появится аккаунт.
  Оба бинарника бандла (`rcdesk-agent`, `rcdesk-host`) подписываются **одним**
  идентификатором `app.rcdesk.agent` (решение 2026-10-21): DR общий, и выданные
  гранты TCC действуют для любого из них — в том числе на экране входа, где
  процесс не может унаследовать права ответственного процесса. Оба несут секцию
  `__CGPreLoginApp,__cgpreloginapp` (кладёт `host/build.rs`, страховка в
  `build-pkg.sh`): без неё CoreGraphics отбрасывает события в сессии LoginWindow.
- **Windows 10 1903+ и 11**, x64. WGC, Media Foundation, SendInput. Тестовый
  стенд владельца — Windows 10 x64.

## 10. Известные ограничения браузеров

- Safari: нет Keyboard Lock API → Cmd+Tab/Cmd+W/Cmd+Q остаются локальными.
  Chrome в fullscreen перехватывает Esc и браузерные сочетания (Cmd+W и т.п.), но **Cmd+Tab на macOS
  забирает сама ОС** даже при выданном разрешении `keyboard-lock` (проверено владельцем 2026-09-22,
  Chrome 153) — из веб-страницы не обойти. При этом нажатие/отпускание Cmd до хоста доходит.
- Не-Mac клиент → macOS-хост (4.6e): та же галочка (ключ `rcdesk.cmd-as-ctrl`, по умолчанию вкл.) подписана
  «Ctrl как Cmd» и МЕНЯЕТ Ctrl и Win местами: Ctrl+C/V/Z работают как на Mac, настоящий Ctrl — через Win (вне полного
  экрана Windows сама забирает Win под меню «Пуск»).
- Mac-клиент → Windows-хост (3.5f): Cmd по умолчанию уходит как Ctrl (переключатель «Cmd как Ctrl»,
  глобальный, в `localStorage`); выключен — Cmd = клавиша Win. ОС хоста клиент узнаёт из
  `ControlMessage::HostInfo`.
- Safari: Clipboard API только по жесту пользователя; синхронизация буфера —
  «по кнопке/по Cmd+V», не фоновая.
  Реализовано (2.5): копирование с хоста — `clipboard.write` с `ClipboardItem`-промисом внутри жеста Ctrl/Cmd+C;
  вставка на хост — `readText` на Ctrl/Cmd+V, Safari показывает кнопку «Вставить».
- H.264 CBP — общий знаменатель; более эффективные профили/кодеки — по
  переговорам SDP, не по умолчанию.
- Автовоспроизведение видео со звуком требует жеста; видео `muted` — нет.
- iPhone Safari: Fullscreen API для `div` нет (включали в 17.2 beta и выключили); адресную строку убирает только
  запуск с домашнего экрана (манифест `standalone`, слайс H4). Android Chrome — Fullscreen API есть.
- Экранная клавиатура: `KeyboardEvent.code` пустой (iOS), `keyCode 229`/`key "Unidentified"` + композиция (Android)
  — надёжен только диф содержимого поля на `input`; поле с `font-size < 16px` iOS приближает; layout viewport при
  клавиатуре на iOS не сжимается — положение считать по `visualViewport`.
- Касания: без `touch-action: none` браузер забирает жест под прокрутку/масштаб и шлёт `pointercancel`; фокус на
  видео при открытой клавиатуре прячет её — тап по видео фокус не переводит, пока показана строка спецклавиш.
- Установка в Chrome из меню работает без service worker (с 108/112); автоподсказка установки требует `fetch`-хендлер —
  нам не нужна.

## 11. Инфраструктура

VPS владельца (FastVPS, Эстония), отдельный пользователь FastPanel `rcdesk`. Docker Compose:
`rcdesk-server` (порт 8080 на localhost) и `coturn` (host-сеть). База сигналинга (3.1) —
в именованном томе `db-data`, смонтированном в `/data`: том пустой при создании наследует
владельца каталога из образа (`/data` создан как `nobody`), поэтому контейнер под `USER
nobody` пишет в него без `chown` на VPS, где у пользователя `rcdesk` нет root. nginx FastPanel: статика
`web/dist`, прокси `/ws` и `/healthz` на 8080, TLS от панели. DNS `rcdesk.app` → VPS;
`turn.rcdesk.app` → тот же IP (без CDN-прокси). Порты: 443 (https/wss), 3478 udp/tcp и
5349 tls (TURN), диапазон relay UDP 49152–65535. Деплой — GitHub Actions по push в `main`
после зелёных гейтов (фаза 3).

Трафик через сервер — только при TURN-релее; при прямом P2P сервер видит лишь
сигналинг. Оценка: офисная работа 1080p 0.5–3 ГБ/час, видео/анимация 4–9 ГБ/час.

**Бюджет трафика (решение владельца, 2026-09-14).** Квота VPS — 10 ТБ/месяц, считается
только исходящий трафик; VPS общий с crewtally, **rcdesk отводится 5 ТБ/месяц**. Релей
через coturn расходует квоту один раз (вход от хоста не считается, выход к клиенту —
считается), то есть 5 ТБ ≈ 550–1250 часов релея видео или ≈ 1700+ часов офисной работы
в месяц; прямые P2P-сеансы квоту не тратят. Механизма учёта и отсечки на сервере пока
нет (долг D22). Реализация (под-шаг 2.4e «инфра: монитор трафика», 2026-09-14):
coturn получает `--prometheus --prometheus-address=127.0.0.1` (host-сеть, метрики на
`127.0.0.1:9641/metrics`); скрипт `infra/traffic-monitor.sh` по cron пользователя `rcdesk`
раз в 10 минут суммирует счётчики coturn `turn_total_traffic_sentb` +
`turn_total_traffic_peer_sentb` (оба направления релея выходят с VPS) и `tx_bytes`
внешнего интерфейса (`/sys/class/net/ens3/statistics/`, весь VPS), копит помесячный итог
в `~/app/traffic/<YYYY-MM>.state` (плоский `key=value` — `jq` на VPS нет; счётчики
сбрасываются при рестарте coturn/VPS, поэтому хранятся последнее значение и накопленная
сумма) и при пересечении порогов 50/80/100 % от 5 ТБ (и 90 % от 10 ТБ по интерфейсу)
шлёт уведомление один раз на порог. **Решения владельца (2026-09-14):** канал —

**LAN-хаб (D47, решения владельца 2026-10-25).** Для изолированной сети без интернета один
компьютер (в первую очередь Windows, только полный режим) — хост и сигнальный сервер сразу:
`rcdesk-server` без фич библиотекой внутри хоста, HTTPS 8443 на всех интерфейсах с вшитым
`web/dist` и самоподписанным сертификатом (ключ P-256 и сертификат на 10 лет хранятся в
`<данные>/hub`), плюс `127.0.0.1:8444` без TLS для хоста на самом хабе; STUN/TURN нет,
аккаунтов/passkey/почты нет (`Authenticated.lan_hub`). Браузер один раз принимает
предупреждение о сертификате. Хост берёт адрес сервера по приоритету флаг `--server` >
`settings.json` каталога данных (поля `server`, `hub`; пишет установщик, хост только читает)
> умолчание; к не боевому `wss://` с недоверенным сертификатом подключается по TOFU —
закрепляет SHA-256 от SPKI в `hub-pin-<slug>.txt`. На Windows хаб живёт в процессе службы
(`hub: true` в `%ProgramData%\rcdesk\settings.json`), установщик выбирает облако / хаб /
подключение к хабу и открывает TCP 8443 в брандмауэре.
